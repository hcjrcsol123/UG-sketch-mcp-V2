# F22 独立 Python Journal

目标是在本机独立 NX batch 中执行显式本地 Python 文件或 UTF-8 脚本内容，传入参数并记录输出、文件和有界 NX 原生对象观察。

调用 `nx_run_journal`：指定全局唯一 `operation_id`、`language: python`、二选一的绝对 `script_path` 或 `script_content`、字符串数组 `args`、现有绝对 `observation_root` 和 1—86400 s `timeout_seconds`。随后调用 `nx_get_journal` 读取持久状态。该模式启动独立会话，不附着桥接模型；已存在 ugraf、run_journal 或桥接 helper 时拒绝。脚本拥有本机用户权限，不是沙箱，必须避免自行启动另一 NX 或访问被其他会话控制的模型。

文件内容在提交时保存为不可复用操作下的执行快照，`__file__` 和 `sys.argv[0]` 是快照路径，相对导入也从快照目录开始；工作目录继承 MCP 宿主，不能假定为原文件目录。参数经官方 `-args` 逐项传入，不经 shell。脚本可产生网络、文件和其他外部副作用；NX Undo 不保证回退。输出文件观察仅递归所选目录的元数据；重解析目录跳过，瞬时、元数据保持和目录外的改动可能遗漏。观察不是隔离事务。

包装器在用户脚本执行前和 finally 后读 NX 已打开零件和可访问 Curves、Bodies、Features，返回零件单位、dirty、对象类型/会话 Tag/JID/名称，以及 Line 端点、Arc 圆心/半径/原生角度。新增/移除是两次可见库存差；打开已有零件也会出现新增，不能等同创建。已关闭、瞬态、其他集合及未采字段的几何变化可能遗漏；Tag 仅在本次会话有效。读取错误明确列出，不能将空差集视为无变化。异常可能已修改模型；不声称已撤销。

固定 Windows 用户配置目录下 `journal-coordination/gate.lock` 和 `active.json` 是跨客户端共享的协调域。监督进程持锁至 runner 自然退出；marker 存在时受控 launcher 拒绝启动。超时 UNKNOWN 不重放、不强杀、不自动解冻，即使稍后退出也保留 marker。`RUNNING` 是最后记录值，不证明监督进程存活。人工恢复需要独立核查进程及外部副作用后处理；没有自动恢复 API。来自产品之外的任意启动或恶意 Journal 不受此协调约束。

官方随附示例说明 C# 可通过 run_journal 使用，但本机两次 `.cs` 探针退出 0 却没有脚本文件输出，实际执行未得到证实，因此本版本拒绝 C#；退出 0 不能作为运行证明。官方 Python 和 `-args` 参考及本机原始探针见 [F22-api-notes](F22-api-notes.md)。

返回的 stdout/stderr 包含原字节文件路径、最多 64 KiB 的 base64 和尽力解码文本（UTF-8 优先，否则使用本机区域编码；不能保证任意脚本编码）。NX Listing Window 未重定向时不在捕获范围，任意 Python 返回值不作为结果。每类模型或文件观察 JSON 不超过 256 KiB 时随 `nx_get_journal` 返回，超过时标记 `available_on_disk` 并提供完整报告路径。

受 gate 或 marker 阻挡时，所有桥接调用（包括状态和 ownership.return）均在派发前拒绝；独立 `nx_get_journal` 仍可读取。包装器要求脚本正常返回；`sys.exit(0)` 作为异常被 finally 观察到，若 runner 退出码为 0，结果按矛盾处理为 UNKNOWN 并保留 marker，不等同正常返回。
