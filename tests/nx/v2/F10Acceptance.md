# F10 sketch projection acceptance plan

## Objective and boundary

Verify that the production operation projects explicitly selected native solid edges and same-part spatial curves into one explicitly selected target Sketch. The request includes an explicit world direction and an `associative` flag. NX2506 `SketchProjectBuilder` exposes no projection vector; the accepted product contract is therefore positive/negative target Sketch normal only. An oblique direction, a direction parallel to the target plane, a zero vector, or a non-finite vector must be rejected during prepare without changing the model. The result must not silently create WAVE, interpart, or external links.

Traceability: `docs/V2.md` F10, the frozen `M3SketchProjectionRequest`, `nx_prepare_sketch_projection`, and `nx_edit_sketch_projection`. F01–F09 are not repeated. This report applies to the recorded NX2506 build and millimetre part units only; one native run does not establish reliability, manufacturing accuracy, regulatory compliance, or behavior on another NX release.

## Configuration, setup, instrumentation, and safety

The designated operator runs the probe or acceptance Journal only in the single idle NX2506 session. The harness must refuse a dirty prior Work Part or active Sketch. It creates a unique standalone millimetre model, records the prior Work Part and Display Part identities, binds only the new model to the production adapter, and uses unique report and Save Copy paths. The probe/acceptance code never starts, restarts, closes, or terminates NX and never opens or modifies an existing user model. Do not run probe variants concurrently.

Instrumentation is the production adapter plus direct NXOpen and UF readback. Capture native source/output type and Tag, source geometry, Sketch frame, direct output geometry, all Sketch geometry, constraints, reference status, feature history, expressions, bodies, model modified state, revision, active Sketch, ownership/write gate, and operation/plan status. Record relation evidence independently from the production verifier, including source feature/object, native relation or builder input, and whether the output updates after a controlled source edit. Classify any WAVE, interpart, linked, or external history/association as a defect. There are no physical instruments; instrument calibration is not applicable. Verify NX version, part units, modeling tolerances, builder tolerance, and Section distance/chaining/angle tolerance settings for every run.

Initial geometry comparison limits are 1e-6 mm for points, radii, and intrinsic lengths, and 1e-7 rad for frame and arc orientation. These are CAD comparison thresholds, not metrology uncertainty or production tolerance. Record the actual NX settings and numeric residuals; if the configured NX tolerance exceeds a comparison limit, stop and report that limitation instead of silently relaxing the acceptance criterion. Use one-to-one matching so a duplicate or missing output cannot pass. Prepare must be read-only. After any native or postcondition failure, use the same transaction Undo mark and prove exact restoration of the complete direct snapshot, dirty state, active Sketch, binding revision, and write gate. If recovery is not proven, record `UNKNOWN`, stop writes, and do not replay or auto-unfreeze.

## Preliminary API discovery evidence

The root-run NXOpen API probe returned from 7/7 builder cases: one spatial Line with both association settings and source edits, one `CommitOperation` control, and parallel partial/full-circle Arcs with both settings. An independent Python oracle re-computed six geometry/association cases from source definitions and target frames: maximum Line residual was 2.55e-15 mm; Arc center residual was at most 1.60e-14 mm; radius residual was zero; arc-length residual was at most 3.56e-15 mm; sweep residual was zero. The associative Line moved the output by 2 mm and undo restored it; the non-associative Line moved no output and undo restored the source. `CPROJ` was present only for associative cases. Raw API evidence and numeric audit are `workspace/v2/evidence/F10-api-probe-8b44e602629540e4bdf1a494bc6ab209.json` and `workspace/v2/evidence/f10-api-numeric-audit-8b44e602629540e4bdf1a494bc6ab209.json`.

This is NXOpen API discovery, not production-adapter or F10 acceptance. It covers no solid Edge, direction request validation, bridge plan lifecycle, fault recovery, Save Copy/reopen, installed MCP, or reliability. The successful probe used `SketchProjectBuilder.Tolerance=0.001` with Section distance/chaining values `0.001` and angle API value `0.5`; these exact settings and their units are recorded, not generalized. `Arc.GetOrientation()` returned `(center, x-axis, y-axis)` and the numeric audit compared sampled curve loci to handle an equivalent reversed/rotated parameter basis. A separate source-relation probe (`workspace/v2/evidence/F10-relation-probe-9401d0bb23314bb48b1bd44a21fcea1a.json`) found the native input Tag through `CPROJ.Section.GetSectionData → GetSectionElementsData → GetSectionElementData1`; `GetOutputCurves` returns an internal source-geometry copy, not the target projection. The target Sketch geometry Tag delta is the projection-output oracle. The final acceptance must still capture and verify the global `Part.Curves` effect of that internal object.

## Reporting and defect handling

The machine-readable report records UTC run/case IDs; NX, NXOpen, bridge, adapter, and acceptance build versions; source/round-trip/report paths; units; `sample_size`; actual modeling and builder/Section tolerances; numeric limits; source request; explicit normalized direction; Sketch frame; source and output Tags/types/native geometry; direct source relation evidence; before/after snapshots; prepare, execute, verify, operation lookup, Undo, Save Copy/reopen, ownership, and write-gate states.

Each defect record includes the smallest fixture, exact tool request or adapter call, direction and association setting, expected source/output geometry, observed source/output geometry, residuals and units, error code/exception, native call/commit evidence, before/after snapshot, Undo outcome, reproduction steps, and retest criterion. Retest on a fresh unique part/report; repeat the failed case plus direct preservation, association or non-association proof, Undo, and Save Copy/reopen. Retain the original failed report. Do not convert an API discovery, controlled fault injection, fake lifecycle test, or one native run into a reliability claim.
