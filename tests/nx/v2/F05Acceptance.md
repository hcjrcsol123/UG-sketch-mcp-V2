# F05 two-line datum-plane acceptance

## Objective and traceability

This acceptance checks F05 through the production `M2OpenModelAdapter` in NX2506 and checks the installed MCP tool with two lines selected from separate existing sketches. The public `nx_prepare_datum_plane` request carries `line1_id` and `line2_id`; the internal request is `Mode="two_lines"` with `Line1Id` and `Line2Id`. F05 is traceable to `docs/V2.md` T05 and the two-line datum-plane requirement in `docs/V2.md`.

The two selected objects must resolve to different native `NXOpen.Line` objects. Two nonparallel coplanar infinite lines, including lines whose intersection is outside one or both finite segments, define one plane. Two distinct parallel lines also define one plane. Missing or wrongly typed objects, a repeated object, a degenerate line, the same infinite line, a skew pair, mixed datum modes, and numerically unsupported near-degenerate pairs must be rejected during prepare without changing the model.

The defining geometry is the pair of infinite lines. Reversing either line's endpoints and swapping the line order must preserve the plane. The normal sign has no required orientation. A feature that exists and reports a two-line method is not sufficient evidence: the native plane must contain all four line endpoints and agree with an independently computed plane equation.

## Test layers, configuration, and safety

- **Analysis:** the harness independently calculates the expected plane from measured native endpoints. This is a deterministic geometry oracle, not a CAD or physical simulation.
- **Inspection:** direct NXOpen reads record each line's runtime type, `JournalIdentifier`, endpoints, and sketch owner; `DatumPlaneBuilder.GetPlane()` records `Plane.Method` and the exact objects returned by `Plane.GetGeometry()`; the feature's parent ancestry records sketch-feature dependencies.
- **Subsystem validation:** each prepare, execute, production verify, and roundtrip uses the compiled production bridge and adapter in the existing NX session.
- **Installed-tool smoke:** the installed STDIO MCP host starts from a saved blank isolated part, creates an F02 tilted fixed datum and separate F01 line sketches, applies and independently checks an intersecting pair, supports a new F01 sketch from that plane, creates a second pair of parallel lines with reversed endpoints, refreshes their IDs, applies and checks the parallel plane, saves/reopens both modes in one copy, and returns ownership.
- **Simulation and physical bench testing:** not applicable to this CAD feature. No hardware, external load, temperature, vibration, acoustic or endurance claim is made.

Build the harness offline. It does not start NX. The designated NX operator runs the journal serially in an idle NX session outside a task environment. The existing Work Part must be saved and unmodified before takeover. The acceptance creates a new, unique millimeter fixture and evidence report under `workspace/v2`; it does not use the user's original part as a fixture. Never run this journal while another agent or user is controlling the same NX session.

Create all native fixture lines and their sketches before capturing final identifiers. NX may renumber journal identifiers as objects are inserted, so resolve and record the current IDs after fixture creation and refresh them after save/reopen. Each mutation test uses its own invisible undo mark and restores the model in a `finally` path. A failed case keeps its unique report and part files for diagnosis; it does not overwrite earlier evidence.

## Instrumentation, calculation, units, and uncertainty

All coordinates and lengths are recorded in millimeters. The harness reads native line endpoints in the part coordinate system, datum origin and normal, the defining `Plane.Method`, `Plane.GetGeometry()`, feature parent ancestry, adapter inspection, and model revision. NX model-value tolerances are 1e-6 mm for plane membership and 1e-7 for normalized direction comparison. These are digital model comparison limits, not manufacturing tolerances or physical measurement uncertainty. There is no external measuring instrument to calibrate. Record the NX version, loaded assembly paths and versions, bridge/adapter build identity, part units, test source version, case inputs, and raw endpoint/plane values. Preserve anomalous data; do not average or discard it.

The independent oracle is computed only from the captured input lines. Let `p0,p1` be line 1 endpoints, `q0,q1` line 2 endpoints, and `u=(p1-p0)/|p1-p0|`, `v=(q1-q0)/|q1-q0|`. Lines of length `<=1e-6 mm` are degenerate. A unit-direction cross norm `|u×v|<=1e-10` is classified as parallel. For those pairs, remove the component of `q0-p0` along `u`; a perpendicular separation `>1e-6 mm` gives `n=normalize(u×(q0-p0))`, while separation `<=1e-6 mm` means the lines are numerically coincident and do not determine a unique plane. A near-parallel pair below the direction threshold is still accepted when its parallel separation is distinct and all four endpoints meet the model-value residual limit. For a pair above the direction threshold, set `n=normalize(u×v)` and check coplanarity with `abs((q0-p0)·n)<=1e-6 mm`; larger separation is skew. For an accepted pair, the independent plane is `(n, d)` where `d=n·p0`.

The native `DatumPlane.Origin` must satisfy `abs(n·origin-d) <= 1e-6 mm`. Compare native and expected unit normals up to sign with `min(|n_native-n_expected|, |n_native+n_expected|)<=1e-7`; the limit applies to vector error, not only the dot product. Compute and record signed residuals for all four endpoints against both the independent plane and the actual native plane; every absolute residual must be at most 1e-6 mm. This check catches native alternate/flip choices that do not contain the input lines, even if NX reports a successful commit. The harness also checks `Plane.Method==TwoLines`, `Plane.GetAlternate()==Three`, exactly the two requested native Lines in `Plane.GetGeometry()`, per-line source Sketch feature IDs, and matching native parent ancestry when the inputs are sketch geometry.

The minimum length, parallel classification, parallel separation, and endpoint coplanarity limits are implementation limits, not inferred physical accuracy. The harness tests below/above boundaries and records raw line geometry and computed cross norm/separation/residual values. If implementation limits change, update the traceable contract and test cases together. Do not silently change a threshold in the acceptance harness.

## Case matrix and procedure

The C# harness defines 32 required top-level cases: one isolated-fixture setup, eleven native-verified positive plane cases, two expected native rollback cases, one F01 support case, fourteen prepare-rejection cases, two independent line-edit/Undo cases, and one save/reopen case. Overall acceptance requires exactly 32 `PASS` cases, no skipped case, and no defects. An expected rollback case passes only when the operation reports `ROLLED_BACK`, records `undo_called`, `semantic_restored`, `geometry_restored`, `history_restored`, and `bodies_restored` as true, preserves the native error text, and returns the complete stable model snapshot to its pre-execution state. A revision change is recorded but is not required to roll back. `UNKNOWN`, `APPLIED`, missing rollback evidence, or a changed model snapshot fails the case. Every prepare call is bracketed by a complete before/after snapshot: adapter inspection, direct feature/sketch/body/curve IDs, fixture line IDs and endpoints, part modified state, and binding revision. A prepare rejection passes only if it throws and this full snapshot is identical. An unexpected plan is recorded as a failure and is never executed.

## Acceptance criteria and failure reporting

Overall `passed` is true only when every required case is `PASS`, no required case is skipped, and the defect list is empty. Any missing native readback, unexpected acceptance/rejection, snapshot mutation during prepare, residual or normal mismatch, wrong geometry association, absent sketch ancestry, roundtrip failure, stale plan accepted, revision unchanged after a valid edit, or failed Undo recovery is a failure.

Each failure record includes the case ID, exact fixture/configuration, request fields, line IDs/types/endpoints, before/after snapshots, exception or unexpected state, independent calculation, native raw values, tolerances, loaded assembly/build information, and NX update/revision data. It also includes executable reproduction steps and an objective retest criterion. A defect retest uses a new unique model/evidence path and repeats the complete affected case plus the full required F05 regression; the original failed report remains unchanged.

JSON evidence is written to `workspace/v2/evidence/F05-acceptance-<run-id>.json`; source and roundtrip parts use matching unique IDs under `workspace/v2/models`. Wrapper start/failure markers are separate records. The report keeps prepare, execute, production verify, independent native oracle, save/reopen, mutation/Undo, and installed smoke evidence distinct.

## Evidence limits

The real-NX run is a functional subsystem test on one NX2506 configuration and one isolated model instance. Geometric prepare limits and NX kernel capabilities are separate: some extremely short or near-parallel lines can satisfy geometric prepare yet fail native Evaluate/readback, so the acceptance requires a verified rollback for the two recorded fixtures. The measured 1e-3 perturbation and 0.01 mm line pass on this fixture only; they do not define universal native-kernel limits. The run does not establish statistical reliability, endurance, cross-version support, manufacturing accuracy, environmental performance, physical load or noise limits, Teamcenter behavior, or standards compliance. The installed smoke is a separate integration check; neither run alone establishes population-wide reliability.
